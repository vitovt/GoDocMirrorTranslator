# AGENTS.md

## Mission
Build and maintain the Go application for the Handwritten Overlay Translator:
- Go core
- Fyne GUI
- OpenAI + Gemini provider adapters
- SVG output in v1
- FODG output in v2

## Source of truth
- `SPEC.md` is the primary product and engineering specification.
- `STATE.md` is the durable project state and workflow memory.
- If `SPEC.md` and implementation differ, align implementation to `SPEC.md` unless the user explicitly decides to revise the specification.

## Required startup workflow
Before any non-trivial work:
1. Read `SPEC.md`.
2. Read `STATE.md`.
3. Read `.codex/local/SNAPSHOT.md` if it exists.
4. Inspect the relevant package boundaries before editing files.
5. Make a short implementation plan.
6. Execute in small, reviewable steps.

## Core engineering rules
- Keep GUI code thin. Business logic belongs in core packages, not in Fyne widgets.
- Preserve a provider-agnostic internal page model and a renderer-agnostic architecture.
- Do not introduce hidden coupling between provider, renderer, CLI, and GUI layers.
- Prefer small, reviewable changes.
- Do not rewrite unrelated files.
- Do not add dependencies unless required by the specification or the task.
- Do not leak provider-specific response formats into domain or renderer layers.
- Do not convert editable SVG text into paths.

## Go rules
- Write idiomatic Go.
- Keep interfaces minimal and purposeful.
- Avoid global mutable state.
- Return wrapped errors with context.
- Keep packages focused.
- Prefer the repository `make` targets over raw `go` commands for routine workflows.
- Run `make fmt` after modifying Go files.

## Validation rules
Before finishing code changes:
- Run `make fmt-check`.
- Run `make test`.
- Run `make lint` if available.
- Prefer `make check` when the standard validation bundle is needed.
- If validation cannot be run, say exactly why.

## Fyne rules
- Keep UI state isolated from application services.
- Do not block the UI thread with network or file operations.
- Use native-first file and folder picker adapters.
- Add or update GUI tests for validation, enabled/disabled state, and success/error flows.

## Provider rules
- Keep OpenAI and Gemini adapters isolated behind one shared provider interface.
- Normalize provider output into the internal page model only once.
- Do not leak provider response formats into the renderer layer.

## Renderer rules
- SVG text must remain editable text, never converted to paths.
- Keep A4 sizing, image scaling, and text overlay logic deterministic.
- Prepare renderer boundaries so FODG can be added without refactoring the domain model.

## State rules
- `STATE.md` is the durable human-readable project state.
- `.codex/local/SNAPSHOT.md` is ephemeral local session state generated by hooks.
- When a task changes architecture, constraints, milestones, or repo layout, update `STATE.md`.

## Safe change rules
- Never run destructive commands such as `rm -rf`, `git clean -fdx`, or `git reset --hard` unless the user explicitly asks.
- Never expose secrets in code, prompts, logs, or generated files.
- Do not commit secrets.
- If a task implies destructive changes, stop and ask for explicit confirmation.

# Personal coding conventions

## Git commits

Create small, incremental, logically separate commits. Each commit should
represent one self-contained change that is easy for a human reviewer to read,
understand, and verify on its own. If the work includes multiple unrelated
fixes, refactors, cleanups, or documentation updates, split them into separate
commits instead of combining them into one large commit. Keep documentation
updates in a separate commit unless they are inseparable from the code change
they describe. Prefer commits that remain understandable in history, review
cleanly, and can be analyzed independently later with tools such as `git blame`
or `git bisect`.

### Common rules for every commit

When you create a git commit message:

- Use the imperative mood.
  - Good: `Add support for nested split panes`
  - Bad: `Added support for nested split panes`
- Aim for 50 characters in the subject line; do not exceed 72.
- Do not end the subject line with a period.
- Make the message specific and descriptive.
- Prefer a one-line commit message for small, obvious changes.
- If additional context is needed, use:
  - first line: short summary in imperative mood
  - blank line
  - concise body explaining why the change was made

### Commit message style

Use Conventional Commits format:

```text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

Rules:

* Prefix each commit with a type such as:

  * `feat:` for a new feature
  * `fix:` for a bug fix
  * `docs:` for documentation-only changes
  * `refactor:` for code restructuring without changing behavior
  * `test:` for adding or updating tests
  * `ci:` for CI changes
  * `build:` for build or dependency changes
  * `chore:` for maintenance tasks
  * `perf:` for performance improvements
  * `style:` for formatting-only changes
* Use an optional scope when it helps identify the affected area, for example:

  * `fix(parser): handle empty input`
  * `docs(readme): clarify setup steps`
* Use `!` or a `BREAKING CHANGE:` footer only for breaking changes.

### Check before committing

Before committing:

* Check `git diff --staged` and ensure the commit message matches the staged change.
* Ensure the message reflects the staged content, not unstaged edits.
* If the staged diff contains unrelated changes, split them into multiple commits.
* If uncertain, propose 2–3 candidate commit messages and choose the clearest one.
